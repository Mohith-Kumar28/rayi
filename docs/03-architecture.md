# Architecture

## Repo layout

```
rayi/
├── CLAUDE.md                  auto-loaded into every session
├── docs/                      this documentation
├── openapi/openapi.json       committed artifact, drift-gated in CI
├── apps/
│   ├── backend/               NestJS + Prisma + Better Auth (Fastify)
│   │   ├── src/
│   │   │   ├── main.ts        entrypoint (role selected by IS_WORKER)
│   │   │   ├── app.module.ts  .common() / .api() / .worker() / .main()
│   │   │   ├── api/           feature modules: health, user, file, funding
│   │   │   ├── architecture/  boundary rules asserted as tests
│   │   │   ├── auth/          Better Auth integration + AuthGuard
│   │   │   ├── authorization/ PermissionService — roles AND money authority
│   │   │   ├── common/        stateless DTOs and types
│   │   │   ├── config/        one registerAs namespace per concern
│   │   │   ├── database/      PrismaService
│   │   │   ├── decorators/    @Operation, @ValidatedBody, auth decorators
│   │   │   ├── guards/        PermissionGuard
│   │   │   ├── ledger/        domain types, repository, retry, purity guard
│   │   │   │                  ── UNREACHABLE from api/ (CI-enforced)
│   │   │   ├── treasury/      use-cases/ (api side) + processors/ (worker side)
│   │   │   ├── shared/        cache, mail, socket
│   │   │   ├── worker/        BullMQ queues + TreasuryWorkerModule
│   │   │   └── types/         declaration merging (fastify.d.ts)
│   │   ├── prisma/schema.prisma
│   │   └── .dependency-cruiser.cjs
│   └── console/               React SPA — TanStack Router + shadcn/ui + Tailwind
└── packages/                  shared with the frontend
    ├── domain/                Money value object, pure ledger logic. NO I/O
    ├── contracts/             Zod operation manifest → openapi.json
    └── api-client/            generated by orval. Never hand-edited
```

**The rule:** `packages/` is code shared with the frontend. Anything the browser will never import
belongs in `apps/backend/src/`.

## Three processes, one image

| Process | Exposure | Role |
| --- | --- | --- |
| `api` | Public ALB | HTTP API. **Holds no Stripe secret key.** No ledger writes |
| `webhooks` | Own ALB rule, no auth stack | Verify signature → insert raw event → 200. Nothing else |
| `worker` | **No target group, no listener, no inbound SG rule** | All money movement |

Same build artifact, different entrypoint. No drift between the code that validated a request and the
code that moves the money.

### How "the payment service is never publicly exposed" is enforced

Four independent layers, because any one can be defeated:

Treasury is **split across the process boundary**, and the split is the mechanism:

| Module | Contains | Bound in |
| --- | --- | --- |
| `TreasuryModule` | use cases — record an intent, return 202 | the api graph |
| `TreasuryWorkerModule` | processors + queue listener — post to the ledger | the **worker graph only** |

Five independent layers, because any one can be defeated:

1. **Structural** — `TreasuryWorkerModule` declares no controller. There is no route to expose, so no
   deployment mistake can expose one.
2. **DI graph** — the processor is bound only in `WorkerModule`. Asserted by test:
   `app.get(AllocateBudgetProcessor, { strict: false })` **throws** on the api application.
3. **Import graph** — dependency-cruiser refuses any import from a controller, `app.module.ts` or
   `main.ts` into `src/ledger/` or `src/treasury/processors/`, **directly or transitively**. Nest's
   module system is a *DI* boundary, not an *import* boundary: nothing stops a file importing a
   service class directly. Each rule is deliberately broken in `src/architecture/boundaries.spec.ts`
   and asserted to fire — a boundary rule that has never been seen to fail is one nobody knows still
   works.
4. **Credentials** — the config schema refuses to boot `api` or `webhooks` if a full `sk_` Stripe key
   is present. An RCE there yields no key and no route to one.
5. **Database** — `rayi_api` has no grant on the ledger schema at all.

Note what is deliberately NOT claimed: both processes are built from **one image**, so the processor
*code* is loaded in the api process. What must not exist is a way to **reach** it.

Importing a treasury *use case* from a controller is allowed and intended — all a use case does is
write a `treasury_command` row inside the caller's transaction.

### The internal "RPC" is a database row

There is **no internal HTTP, no mTLS, no gRPC, no signed assertion.** The api writes a
`treasury_command` row and enqueues a job **inside the caller's transaction**; the worker picks it up.

Durable, replayable, auditable in plain SQL — and valid for a payout sweep seven days later, which a
60-second signed token could never be. The worker has no listening socket, so there is nothing to
authenticate because there is nothing to call. Requirement 5 is satisfied by **deleting the channel**
rather than encrypting it.

The worker treats the job payload as **a pointer, never an instruction** — it re-derives everything
authoritative from the database, including re-checking authorization, because a weekly sweep executes
long after the request when the approver may have been removed. Both cases are tested: authority
revoked after the request, and the member removed from the organization, each of which fails the
command at the worker with nothing posted.

Account identities are **derived, never accepted**. `ledger.account_for_campaign(campaignId, role,
currency)` reads the owning organization from the campaign row and returns (creating on first use)
the one account for that scope. A caller names what it is acting on; the database decides which
account that is. There is no parameter through which "post to a different account" can be expressed.

**Discovery is two mechanisms, and only one is load-bearing.** `LISTEN/NOTIFY` gives low latency and
is fire-and-forget — a notification raised while no worker is connected is gone, and Postgres drops
them entirely if its queue overflows. The **poll** over `treasury_command WHERE status = 'pending'` is
the correctness mechanism, because rows survive a crash, a deploy, a failover and a restore. Deleting
the LISTEN would make the system slower; deleting the poll would make it lose money.

## Request flow

```
Browser (app.rayi.com)
  → CloudFront  /api/* behaviour  → ALB → api
      __Host- session cookie, same-origin: no CORS, no preflight, no SameSite=None
  → AppThrottlerGuard   rate limit, keyed on req.ip (trustProxy-derived)
  → AuthGuard           GLOBAL. Authentication. Opt out with @PublicAuth()
  → PermissionGuard     GLOBAL. Authorization. Deny-by-default for @Operation() routes
  → Controller          HTTP only. No business logic
  → Application service transaction + authorization boundary
  → Domain              pure. No @nestjs/*, no @prisma/*, no I/O
  → Repository          the only place SQL lives
```

Money-moving requests stop at the application service: it writes an intent + enqueues a job in one
transaction and returns **202**. The worker does the rest.

**Authorization runs at two layers, and both are needed.**

| Layer | Question | Why it cannot answer the other |
| --- | --- | --- |
| `PermissionGuard` | *Could this caller hold this permission anywhere in this organization?* | It sees only the URL. A workspace-scoped permission is not derivable from a path that names a campaign. |
| Application service | *May you do this, here, for this amount?* | It runs after routing, so it cannot fail closed for a route that forgot to declare access. |

The guard's check is a **ceiling**, and sound because it is a superset: a permission absent from every
role the user holds in the organization cannot be granted by narrowing to one workspace. The service
then reads the workspace **off the campaign row** — so the scope a permission is evaluated against is
a database fact, not a request parameter.

For a route marked `movesMoney`, the guard additionally requires a `MoneyAuthority` row to exist. The
**amount** is checked by the service, because the guard cannot see it — and pretending otherwise is
exactly how a per-row limit ends up not applying to a batch.

Tenant scope comes from the **URL**, never from `session.activeOrganizationId`: that field is shared
mutable state across browser tabs, so an agency operator with two clients open would otherwise have
requests authorised against whichever org they last switched to.

A caller who is not a member gets **404, not 403**. A 403 confirms the organization exists, which
turns every tenant route into an enumeration oracle.

## The contract pipeline

```
packages/contracts (Zod manifest)
        │  pure script, no Nest boot
        ▼
   openapi/openapi.json   ← committed, drift-gated in CI
        │  orval
        ▼
packages/api-client  →  typed client + TanStack Query hooks + MSW handlers
```

One manifest entry drives four things that otherwise drift: server validation, response
serialization, the OpenAPI document, and the generated client. `@Operation('allocateBudget')` takes
its method, path and authorization metadata from that entry, so a route cannot exist at a path the
published spec does not describe.

CI regenerates both and fails if either is stale. **Verified firing.**

This is also what lets the frontend be built before the backend exists: generate the client from the
manifest, mock with MSW, build screens.

## Layering

```
Controller → Application service → Domain → Repository port
                                                 ↑
                                       Adapter (Prisma, Stripe)
```

- **Controller** — HTTP only. Longer than ~10 lines means logic has leaked in.
- **Application service** — the transaction and authorization boundary. One public method per use
  case, named for the use case (`allocateBudget`, not `update`).
- **Domain** — pure. No framework, no clock, no randomness; inject those.
- **Repository** — the only place SQL lives. Returns domain types, never Prisma models.

**Ports for aggregates, direct Prisma for reads.** A repository wrapping `findMany` is the thin leaky
wrapper the critics are right about. One enforcing balanced double-entry and taking row locks is
hiding real complexity and earns its place. Methods are named by intent (`findUnsettledForOrg`),
never `find(condition)`.

## Data

**PostgreSQL 17 on AWS RDS**, Multi-AZ, PITR. Four roles with different grants:

| Role | Grants |
| --- | --- |
| `rayi_migrator` | Schema changes only — and *not* on the ledger schema |
| `rayi_api` | Read app schema, write intents. **No ledger writes** |
| `rayi_worker` | Ledger INSERT (never UPDATE/DELETE), read app schema |
| `rayi_webhooks` | INSERT on the raw-event table and nothing else |

Ledger tables are append-only at the database level: `REVOKE UPDATE, DELETE` plus a trigger that
raises. Corrections are reversing entries, which is what an auditor expects to see.

Local development uses a Postgres 17 container on port **55432**.

## Queues

| Queue | Used for | Why |
| --- | --- | --- |
| **BullMQ** (Redis) | Emails, notifications, media processing, TikTok polling, reports | Mature tooling, Bull Board UI. At-least-once is fine here |
| **Postgres-backed** | The money path only | The job must commit **inside the same transaction as the ledger write**. Redis cannot join a Postgres transaction, so BullMQ there would reintroduce the dual-write bug |

## Frontend

**One origin for everything authenticated.** `app.rayi.com` — CloudFront default behaviour to S3
serving one Vite + TanStack Router SPA with both authed route trees (`/` console, `/me` creator),
code-split by population. An `/api/*` behaviour points at the ALB.

Because the API is same-origin: `__Host-rayi.session` is host-only, there is no CORS, no preflight,
no `SameSite=None`, no CHIPS workaround, and `connect-src 'self'` is literally true.

`rayi.com` serves the public SSR surface (`/@handle`, payment links). **It renders creator-authored
content and is same-SITE with the app**, so `SameSite=Lax` would attach the session cookie — every
mutation must therefore check `Origin` is the exact app origin and `Sec-Fetch-Site` is `same-origin`.

## Money on the wire

```json
{ "amountMinor": "15000", "currency": "USD", "exponent": 2 }
```

A **string** of integer minor units, declared in OpenAPI as `type: string, pattern: ^-?(0|[1-9][0-9]*)$`
so codegen emits a branded type rather than a number, with a **server-supplied exponent**. A JSON
number loses precision past 2^53, and the `?? 2` fallback silently misformats 3-decimal currencies by
10×.

A Zod refinement at the generated-client boundary rejects empty and non-integral values before any
component sees them; past that boundary the only money type is `bigint`.
